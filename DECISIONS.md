This register converts locked architecture rules, owner-confirmed answers, and analyst-proposed decisions into a single controlled list. Every row has a status and an owner. Items not explicitly confirmed by the Project Owner or fixed in an existing source document are marked `PROPOSED`, `INFERRED`, `UNRESOLVED`, `BLOCKED`, or — from Phase 01 onward — `APPROVED_IMPL`. **Never bare `APPROVED`**, which is reserved for owner-stated or source-document-fixed decisions, per Phase 00 hard rules.

**Row ordering is by insertion, not by ID.** `D-027` and `D-028` appear between `D-022` and `D-023` in the Phase 00 table because they were added during Phase 00's review remediation. Stated explicitly so a mechanical consumer does not assume ID order (Reviewer Finding F-11).

The sole authoritative record of what the owner actually said at intake is `INTAKE_RECORD.md`. Any row citing owner confirmation must trace to it.

### Status vocabulary

`templates/DECISION_REGISTER_TEMPLATE.md` defines a register enum (PROPOSED / APPROVED / REJECTED / SUPERSEDED / UNRESOLVED / BLOCKED), while `00_MASTER_START_HERE.md` mandates a *material-input* vocabulary (CONFIRMED / INFERRED / PROPOSED / UNRESOLVED / BLOCKED). These are different axes. This register uses the template enum for the Status column, mapped as follows:

| Status | Meaning | Material-input equivalent |
|---|---|---|
| `APPROVED` | Locked — owner-stated at intake, or already fixed in a governing source document | CONFIRMED |
| `APPROVED_IMPL` | A reversible technical/implementation decision made by a phase owner inside that phase's delegated mandate. **Not owner-stated.** Overridable by the Project Owner at the reversal cost recorded in the row | INFERRED (implementation scope) |
| `INFERRED` | A reasonable reading derived from confirmed context; needs owner confirmation | INFERRED |
| `PROPOSED` | Specialist recommendation awaiting owner sign-off | PROPOSED |
| `UNRESOLVED` | Genuinely unknown; owner input required | UNRESOLVED |
| `BLOCKED` | Needs an external dependency or access that does not yet exist | BLOCKED |

Every Status cell contains exactly one of these bare tokens — no qualifiers or parenthetical modifiers — so the register stays machine-readable under Architecture Rule 1. Qualifications belong in the Decision or Rationale column. None of them changes policy, scope, architecture, or any gate. Anything that *would* touch policy or require an outward-facing action is `PROPOSED` and waits for the owner — see `D-030`.

**Corrected 2026-07-29 (Reviewer Finding F-07).** These six rows were originally written with the bare token `APPROVED`, distinguished from owner-locked decisions only by this prose note. Nobody asked the owner. The prose note distinguishing them was not in the column a machine reads.
